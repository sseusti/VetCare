# DWH — SQL-скрипты: схема, staging, витрины и метрики

Аналитическая часть VetCare в PostgreSQL 16. База поднимается из корня репозитория командой `docker compose up -d`.

| Файл | Что делает |
| --- | --- |
| `01_schema.sql` | схема `oltp` — рабочая база клиники: 8 таблиц с ключами, связями и проверками |
| `02_load.sql` | загрузка CSV из генератора: `raw` (всё текстом) → `oltp` (типы и ограничения) |
| `03_checks.sql` | проверки качества данных; падает с ошибкой, если есть нарушения |
| `04_marts.sql` | staging (`stg`) и витрины по схеме «звезда» (`mart`) |
| `05_mart_checks.sql` | проверки витрин: полнота фактов, сходимость выручки с `oltp` |
| `metrics/*.sql` | бизнес-метрики — представления в схеме `metrics`: выручка, врачи, неявки, загрузка, когорты, LTV, отток |
| `06_metric_checks.sql` | проверки метрик: суммы сходятся с витринами, доли дают 100%, LTV не убывает, сплит A/B-теста без перекоса |

## Быстрый старт

Из корня репозитория, при установленном Docker и окружении генератора (`data-generator/.venv`):

```bash
make all      # база, данные, схема, загрузка, витрины, метрики и все проверки
make psql     # открыть консоль базы
```

По отдельности: `make up`, `make data`, `make schema`, `make load`, `make marts`, `make metrics`, `make checks`. Все скрипты можно запускать повторно.

## Загрузка данных

```
data-generator/data/raw/*.csv  --\copy-->  raw.*  (все колонки TEXT)  --INSERT ... SELECT-->  oltp.*
```

CSV попадают в контейнер через том `./data-generator/data/raw:/data/raw:ro` в `docker-compose.yml`.

- **Зачем слой `raw`.** Файл ложится как есть, и загрузка не падает на типах; приведение типов при переносе в `oltp` даёт понятную ошибку на конкретной колонке. Так устроена загрузка в настоящих хранилищах: сырые данные отдельно, очищенные отдельно.
- **`OVERRIDING SYSTEM VALUE`.** Колонки `id` объявлены `GENERATED ALWAYS`, и `COPY` в них не пишет. `INSERT ... OVERRIDING SYSTEM VALUE` сохраняет id из генератора — иначе развалились бы связи.
- **Одна транзакция.** Очистка и перенос всех таблиц — `BEGIN ... COMMIT`: при ошибке база остаётся в прежнем состоянии, а не наполовину загруженной.
- **Порядок.** `TRUNCATE ... CASCADE` очищает и зависимые таблицы, поэтому его порядок не важен; `INSERT` идут от таблиц, на которые ссылаются, к ссылающимся.
- **Счётчики id.** После вставки своих id счётчик identity сдвигается на максимум (`setval`), иначе следующий обычный `INSERT` получил бы `id = 1` и упал на дубликате.

## Проверки качества

`03_checks.sql` считает нарушения по 20 проверкам и печатает таблицу «проверка — нарушений — итог»:

- число строк в `raw` и `oltp` совпадает для каждой таблицы;
- оплата есть ровно у состоявшихся приёмов и не раньше начала приёма;
- приём не раньше найма врача и регистрации владельца, животное родилось до регистрации владельца;
- у каждого животного медкарта, приём в филиале своего врача, хирургию ведут хирурги;
- каждая прививка — результат состоявшегося приёма-вакцинации;
- запланированные приёмы идут позже всех прошедших.

Если хоть одна проверка нашла нарушения, скрипт завершается с ошибкой — так его можно ставить в CI.

## Схема `oltp`

`branches` → `doctors`; `owners` → `pets` → `medical_cards` → `visits` → `payments`; `pets` → `vaccinations`. Приём ссылается на медкарту, врача и филиал; у животного одна медкарта, у приёма — не больше одной оплаты.

Решения, которые стоит знать:

- **Ключи** — `BIGINT GENERATED ALWAYS AS IDENTITY`: стандарт SQL, id нельзя случайно вставить руками.
- **`ON DELETE RESTRICT`** на всех связях: удалить владельца с животными, врача с приёмами или оплаченный приём нельзя — история и выручка не теряются.
- **Деньги** — `NUMERIC(10, 2)`, а не `float`: точная арифметика без ошибок округления.
- **Время** — `TIMESTAMPTZ`: момент времени с часовым поясом.
- **Списки значений** (статус и тип приёма, способ оплаты, пол, размер) хранятся латиницей и проверяются через `CHECK`; русские подписи появятся на дашборде.
- **Бизнес-правила в базе:** запись не позже приёма (`booked_at <= scheduled_at`), диагноз только у состоявшегося приёма, скидка от 0 до 100%.
- **Индексы** на все внешние ключи (на колонки с `UNIQUE` индекс создаётся сам) и на дату приёма — по ней фильтрует почти вся аналитика.

## Отличия от модели лабы 1

Модель предметной области взята из [лабы 1](../docs/lab1/README.md). При переходе к аналитической базе часть решений пересмотрена:

| В лабе 1 | Здесь | Почему |
| --- | --- | --- |
| возраст животного `age` | дата рождения `birth_date` | возраст меняется каждый год, хранить его — значит хранить устаревшие данные; возраст вычисляется на любую дату |
| адрес филиала текстом в приёме | таблица `branches`, у приёма `branch_id` | филиал — отдельная сущность; текстовый адрес даёт опечатки и не группируется в отчётах |
| отдельные `date` и `time` приёма | одно поле `scheduled_at TIMESTAMPTZ` | один момент времени проще сравнивать, сортировать и считать интервалы |
| прививки строкой в медкарте | таблица `vaccinations` (животное, вакцина, дата) | список в одной ячейке нарушает 1НФ; отдельные строки позволяют считать сезонность прививок |
| общая таблица `PersonalData` для владельца и врача | ФИО и телефон прямо в `owners` и `doctors` | общих сценариев у владельцев и врачей нет, а общая таблица добавляет лишний JOIN в каждый запрос |
| — | дата записи `booked_at` у приёма | неявки сильно зависят от того, как заранее записались |
| — | `reminder_sent` у приёма | флаг SMS-напоминания для A/B-анализа неявок |
| — | `hired_at` у врача, `registered_at` у владельца | нужны для загрузки врачей с учётом стажа и для когорт клиентов |
| врач в приёме: в тексте «несколько врачей», в диаграмме — один | один `doctor_id` | как на диаграмме классов: приём ведёт один врач, это проще для загрузки и выручки по врачам |
| оплата: `price` и `discount` | `amount` (цена до скидки) и `discount` в процентах | смысл полей описан в `COMMENT ON COLUMN`; выручка считается как `amount * (1 - discount / 100)` |

## Витрины: схема «звезда»

```
oltp (рабочая база)  -->  stg (представления: подготовка)  -->  mart (таблицы: звезда)
```

```
                 dim_date
                    |
  dim_doctor -- fact_visits -- dim_pet
                    |   |
           dim_branch   dim_owner          fact_payments ссылается на те же измерения
```

**Слой `stg`** — представления, где один раз решаются «неудобные» вопросы: дата и час по московскому времени (`AT TIME ZONE 'Europe/Moscow'`), выручка после скидки, связь приёма с животным и владельцем. Витрины строятся уже из него.

**Факты** — то, что считаем. Главное в факте — **зерно**: что означает одна строка.

| Таблица | Зерно | Что внутри |
| --- | --- | --- |
| `fact_visits` | один приём в любом статусе | ключи измерений; тип и статус; флаги `is_completed`, `is_no_show`, `is_cancelled`; `reminder_sent`; `lead_days` (за сколько дней записались); час приёма; возраст животного; выручка (0, если оплаты нет) |
| `fact_payments` | одна оплата | ключи измерений, дата оплаты и приёма; услуга, способ оплаты; цена, скидка в процентах и рублях, выручка после скидки |

**Измерения** — то, по чему фильтруют и группируют.

| Таблица | Ключ | Что внутри |
| --- | --- | --- |
| `dim_date` | `date` | каждый день периода: год, квартал, месяц и его название, начало месяца и недели, день недели, выходной, сезон |
| `dim_branch` | `branch_id` | название и адрес филиала |
| `dim_doctor` | `doctor_id` | полное и короткое ФИО, специализация, филиал, дата найма, новичок ли (нанят внутри периода) |
| `dim_pet` | `pet_id` | вид, порода, размер, пол, дата рождения, есть ли хроническое заболевание и аллергия |
| `dim_owner` | `owner_id` | дата регистрации, первый состоявшийся визит, **когорта** — месяц первого визита, число животных |

Решения, которые стоит знать:

- **Витрины — таблицы, staging — представления.** Витрины много раз читает дашборд, их выгодно посчитать один раз; staging нужен только при пересборке.
- **`LEFT JOIN` к оплатам** в `fact_visits`: у неявок и отмен оплаты нет, обычный `JOIN` молча выкинул бы 16% приёмов. Выручка без оплаты — `0`, а не `NULL`, иначе суммы и средние посчитаются неправильно.
- **Календарь генерируется** (`generate_series`), а не берётся из данных: в нём есть все дни, даже без приёмов, и на графиках нет «дыр».
- **Первичные и внешние ключи на витринах:** первичный ключ проверяет зерно (если JOIN размножил строки, он не создастся), внешние — что у каждого факта есть все измерения.

Пример — доля неявок по дням недели:

```sql
SELECT d.weekday_name, round(100 * avg(f.is_no_show::int), 1) AS no_show_pct
FROM mart.fact_visits AS f
JOIN mart.dim_date AS d ON d.date = f.visit_date
WHERE f.status IN ('completed', 'no_show')
GROUP BY d.weekday, d.weekday_name
ORDER BY d.weekday;
```

## Метрики: схема `metrics`

```
mart (витрины)  -->  metrics (представления: ответы на вопросы бизнеса)  -->  дашборд
```

Каждый файл в `metrics/` отвечает на свой вопрос и создаёт несколько представлений. Представление не хранит данных, а считается при каждом обращении, поэтому метрики всегда совпадают с витринами. DataLens читает их как обычные таблицы. Все запросы выполняются меньше чем за 0,1 с.

| Файл | Вопрос бизнеса | Представления |
| --- | --- | --- |
| `00_schema.sql` | границы данных | `period` — первый и последний день, последний полный месяц |
| `01_revenue.sql` | как меняются выручка и средний чек? | `revenue_monthly` (MoM, YoY, с начала года), `revenue_by_visit_type`, `revenue_by_branch_monthly` |
| `02_doctors.sql` | кто приносит больше денег? | `doctor_performance` (место и доля в филиале), `specialization_summary` |
| `03_no_show.sql` | когда и почему не приходят? | `no_show_by_weekday`, `_by_lead_time`, `_by_hour`, `_by_species`, `no_show_lost_revenue` |
| `04_utilization.sql` | равномерно ли загружены врачи? | `doctor_load` (приёмы в день относительно медианы), `branch_load_monthly` |
| `05_retention.sql` | возвращаются ли клиенты? | `cohort_retention` (матрица когорт), `retention_curve`, `repeat_rate` |
| `06_ltv.sql` | сколько приносит клиент? | `cohort_ltv`, `ltv_curve`, `ltv_12m_by_species` |
| `07_churn.sql` | кого мы теряем? | `owner_status`, `churn_summary`, `churn_by_pets`, `at_risk_owners` — кому напомнить первым |
| `08_experiment.sql` | снижают ли SMS неявки? | `experiment_visits` (участники A/B-теста с группой и ковариатами), `experiment_summary`, `experiment_naive_comparison`, `experiment_weekly` |

```sql
SELECT * FROM metrics.revenue_monthly;
SELECT * FROM metrics.cohort_retention WHERE month_n <= 12 ORDER BY cohort_month, month_n;
```

Решения, которые стоит знать:

- **Только полные месяцы.** Последний месяц, если он не закончился, выглядел бы как падение выручки; приёмы в будущем (`scheduled`) не считаются.
- **Неявки считаются от «пришёл или нет»**: отменённые приёмы не учитываются — о них предупредили, слот можно было отдать. Приёмы с SMS-напоминанием исключены, чтобы не смешивать эффекты; эксперимент разбирается отдельно.
- **Когорты — только новые клиенты.** У клиентов, пришедших до начала данных, «первый визит» в данных не первый, и они раздули бы ранние когорты (цензурирование слева). У свежих когорт ещё нет поздних месяцев — их просто нет в матрице (цензурирование справа).
- **Сетка «когорта × месяц».** Месяцы без визитов дают строку с нулём, а не пропадают — иначе удержание выглядело бы выше.
- **LTV делится на всю когорту**, а не на активных: ушедшие клиенты тоже входят в среднее.
- **Отток — по давности последнего визита**: до 180 дней — активный, 181–365 — засыпающий, больше года — ушёл. Плановый осмотр раз в год, поэтому меньше года без визита ещё не отток. Пороги — договорённость с бизнесом.
- **В A/B-тест входят только записи хотя бы за день**: при записи в тот же день SMS не отправляют, и в сравнении «с SMS / без SMS» по всем приёмам они смещают контроль. Статистический разбор — в [`analysis/`](../analysis).
- **После `make marts` нужен `make metrics`**: витрины пересоздаются через `DROP ... CASCADE` и забирают представления с собой. `make all` делает это сам.

Что видно в данных:

- **Выручка** за последний год выросла на 5–44% к тому же месяцу прошлого года; пик — май–июнь, провал — февраль.
- **Хирургия** — 7% приёмов, но 34% выручки: средний чек 13,4 тыс. ₽ против 1,3 тыс. ₽ у осмотра. Оба хирурга дают больше половины выручки своих филиалов и загружены на 35–42% выше медианы.
- **Неявки:** в понедельник 13,7% против 7,5–8,7% в другие дни; при записи за 15+ дней — 15% против 7,4% при записи накануне; утренние 9–10 часов — около 12%.
- **Удержание:** в следующем месяце после первого визита приходят 29% новых клиентов, через 12 месяцев — 20%; хотя бы раз в течение 6 месяцев возвращаются 79%.
- **LTV** нового клиента — 3,9 тыс. ₽ в первый месяц, 9,4 тыс. ₽ за полгода, 14 тыс. ₽ за год.
- **Отток** почти в 5 раз ниже у владельцев трёх и более животных: 5,7% против 30,6% у владельцев одного.
