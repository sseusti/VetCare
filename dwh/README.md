# DWH — SQL-скрипты: схема, staging, витрины и метрики

Аналитическая часть VetCare в PostgreSQL 16. База поднимается из корня репозитория командой `docker compose up -d`.

| Файл | Что делает |
| --- | --- |
| `01_schema.sql` | схема `oltp` — рабочая база клиники: 8 таблиц с ключами, связями и проверками |
| `02_load.sql` | загрузка CSV из генератора: `raw` (всё текстом) → `oltp` (типы и ограничения) |
| `03_checks.sql` | проверки качества данных; падает с ошибкой, если есть нарушения |

## Быстрый старт

Из корня репозитория, при установленном Docker и окружении генератора (`data-generator/.venv`):

```bash
make all      # поднять базу, сгенерировать данные, создать схему, загрузить, проверить
make psql     # открыть консоль базы
```

По отдельности: `make up`, `make data`, `make schema`, `make load`, `make checks`. Все скрипты можно запускать повторно.

## Загрузка данных

```
data-generator/data/raw/*.csv  --\copy-->  raw.*  (все колонки TEXT)  --INSERT ... SELECT-->  oltp.*
```

CSV попадают в контейнер через том `./data-generator/data/raw:/data/raw:ro` в `docker-compose.yml`.

- **Зачем слой `raw`.** Файл ложится как есть, и загрузка не падает на типах; приведение типов при переносе в `oltp` даёт понятную ошибку на конкретной колонке. Так устроена загрузка в настоящих хранилищах: сырые данные отдельно, очищенные отдельно.
- **`OVERRIDING SYSTEM VALUE`.** Колонки `id` объявлены `GENERATED ALWAYS`, и `COPY` в них не пишет. `INSERT ... OVERRIDING SYSTEM VALUE` сохраняет id из генератора — иначе развалились бы связи.
- **Одна транзакция.** Очистка и перенос всех таблиц — `BEGIN ... COMMIT`: при ошибке база остаётся в прежнем состоянии, а не наполовину загруженной.
- **Порядок.** `TRUNCATE ... CASCADE` очищает и зависимые таблицы, поэтому его порядок не важен; `INSERT` идут от таблиц, на которые ссылаются, к ссылающимся.
- **Счётчики id.** После вставки своих id счётчик identity сдвигается на максимум (`setval`), иначе следующий обычный `INSERT` получил бы `id = 1` и упал на дубликате.

## Проверки качества

`03_checks.sql` считает нарушения по 20 проверкам и печатает таблицу «проверка — нарушений — итог»:

- число строк в `raw` и `oltp` совпадает для каждой таблицы;
- оплата есть ровно у состоявшихся приёмов и не раньше начала приёма;
- приём не раньше найма врача и регистрации владельца, животное родилось до регистрации владельца;
- у каждого животного медкарта, приём в филиале своего врача, хирургию ведут хирурги;
- каждая прививка — результат состоявшегося приёма-вакцинации;
- запланированные приёмы идут позже всех прошедших.

Если хоть одна проверка нашла нарушения, скрипт завершается с ошибкой — так его можно ставить в CI.

## Схема `oltp`

`branches` → `doctors`; `owners` → `pets` → `medical_cards` → `visits` → `payments`; `pets` → `vaccinations`. Приём ссылается на медкарту, врача и филиал; у животного одна медкарта, у приёма — не больше одной оплаты.

Решения, которые стоит знать:

- **Ключи** — `BIGINT GENERATED ALWAYS AS IDENTITY`: стандарт SQL, id нельзя случайно вставить руками.
- **`ON DELETE RESTRICT`** на всех связях: удалить владельца с животными, врача с приёмами или оплаченный приём нельзя — история и выручка не теряются.
- **Деньги** — `NUMERIC(10, 2)`, а не `float`: точная арифметика без ошибок округления.
- **Время** — `TIMESTAMPTZ`: момент времени с часовым поясом.
- **Списки значений** (статус и тип приёма, способ оплаты, пол, размер) хранятся латиницей и проверяются через `CHECK`; русские подписи появятся на дашборде.
- **Бизнес-правила в базе:** запись не позже приёма (`booked_at <= scheduled_at`), диагноз только у состоявшегося приёма, скидка от 0 до 100%.
- **Индексы** на все внешние ключи (на колонки с `UNIQUE` индекс создаётся сам) и на дату приёма — по ней фильтрует почти вся аналитика.

## Отличия от модели лабы 1

Модель предметной области взята из [лабы 1](../docs/lab1/README.md). При переходе к аналитической базе часть решений пересмотрена:

| В лабе 1 | Здесь | Почему |
| --- | --- | --- |
| возраст животного `age` | дата рождения `birth_date` | возраст меняется каждый год, хранить его — значит хранить устаревшие данные; возраст вычисляется на любую дату |
| адрес филиала текстом в приёме | таблица `branches`, у приёма `branch_id` | филиал — отдельная сущность; текстовый адрес даёт опечатки и не группируется в отчётах |
| отдельные `date` и `time` приёма | одно поле `scheduled_at TIMESTAMPTZ` | один момент времени проще сравнивать, сортировать и считать интервалы |
| прививки строкой в медкарте | таблица `vaccinations` (животное, вакцина, дата) | список в одной ячейке нарушает 1НФ; отдельные строки позволяют считать сезонность прививок |
| общая таблица `PersonalData` для владельца и врача | ФИО и телефон прямо в `owners` и `doctors` | общих сценариев у владельцев и врачей нет, а общая таблица добавляет лишний JOIN в каждый запрос |
| — | дата записи `booked_at` у приёма | неявки сильно зависят от того, как заранее записались |
| — | `reminder_sent` у приёма | флаг SMS-напоминания для A/B-анализа неявок |
| — | `hired_at` у врача, `registered_at` у владельца | нужны для загрузки врачей с учётом стажа и для когорт клиентов |
| врач в приёме: в тексте «несколько врачей», в диаграмме — один | один `doctor_id` | как на диаграмме классов: приём ведёт один врач, это проще для загрузки и выручки по врачам |
| оплата: `price` и `discount` | `amount` (цена до скидки) и `discount` в процентах | смысл полей описан в `COMMENT ON COLUMN`; выручка считается как `amount * (1 - discount / 100)` |
